# 02 인증 데이터·비공개 설정 기반

2026-10-18 첫 구현 당시의 기록이다. 이 문서의 데이터 구조·설정 로딩 이후 로그인·계정 관리·업무 배정 화면까지 구현했다. 현재 사용법과 실제 시험 상태는 [02 인수인계](phase-02-guide.md), [진행상황](STATUS.md)을 따른다. 아래 설명과 [첫 구현 기록](history/2026-10-18-phase-02-auth-foundation.md)은 당시 범위를 보존한다.

## 추가한 데이터

| 테이블 | 내용·제약 |
|---|---|
| login_accounts | 기존 users ID를 참조하는 사전 등록 이메일, 인증 버전. 소문자·공백 제거 이메일과 고유 제약. 원본 users.auth_subject는 보존하며 새 연결로 자동 이관하지 않음 |
| email_ownership_checks | 확인 대상 이메일·결과·방법·확인자·시각의 추가형 이력. 기록 없음은 확인 대기. 이메일 변경 후 과거 이메일 확인을 새 이메일에 재사용하지 않음 |
| auth_identities | 내부 계정과 제공자/issuer/subject 연결, 고유 제약, 기본 비활성. 기존 이메일 일치만으로 연결하지 않음 |
| auth_sessions | 원 토큰 대신 SHA-256 해시, 사용자/인증 연결 복합 FK, 인증 버전, 발급·활동·만료·폐기·추가 본인 확인 시각. 최대 8시간, 계정당 미폐기 2슬롯 |
| account_audit_events | 과제에 속하지 않는 계정 관리 감사. 행위자·대상·요청·사유·변경 전후. 요청 중복 제약 및 수정/삭제/TRUNCATE 차단 |

세션 슬롯은 1/2만 허용하고 미폐기 슬롯의 고유 인덱스로 동시 삽입도 제한한다. 만료된 행은 폐기 처리 후 슬롯을 재사용하되 이력은 남긴다. 원 토큰·Google 토큰·client secret을 저장하는 열은 없다. 감사 payload에 비밀정보를 넣지 않는 책임은 후속 서비스에서도 지켜야 한다.

DB는 사전 등록/인증 연결의 참조 무결성을 제공한다. 계정 활성·인증 연결 활성·현재 이메일 확인·현재 권한·유휴 만료 판단, 정지/역할 변경 시 세션 폐기, 수기 확인을 수행할 수 있는 담당자/관리자 구분은 후속 서버 서비스에서 구현한다. 현재 DB 구조만으로 이러한 정책이 시행된다고 표현하지 않는다.

기존 01 마이그레이션은 수정하지 않고 `1792281600000_auth_foundation.sql`을 추가했다. down은 이력 보존을 위해 거부한다. 개발·시험 public에는 합계 13개 테이블이 있으며 새 로그인 계정·인증 연결·세션은 0개다. 실제 관리자를 생성하지 않았다.

## 비공개 설정 로딩

`scripts/google-config.mjs`는 절대 경로의 저장소 밖 파일만 읽고 웹 클라이언트 형식·ID/Secret 형식을 검사한다. realpath로 저장소 내부를 가리키는 경로도 거부한다. 실패 메시지는 입력값·경로·파싱 원문을 포함하지 않는다. JSON의 인증 서버 URL은 사용하지 않는다.

`scripts/local.mjs`에서 `BOOT_ERP_GOOGLE_OAUTH_FILE`을 지정하면 dev/start에만 서버 환경변수로 공급한다. 해당 경로와 Google 값은 migrate/seed/test:db 자식 환경에서 제거한다. 로더는 로그인 엔드포인트가 아니며 실제 키 유효성을 Google에 조회하지 않는다. 실행 예시는 [로컬 연결 안내](google-login-setup.md)에 있다.

## 검수와 다음 작업

신규 계정/Google 인증정보 없이 수행한 단위·가상 DB 검수와 실제 비공개 파일의 형식/비노출 검수를 구분했다. 확인된 불변 이력·원자성·세션 슬롯 제한은 데이터 기반 수준이며 A-01~A-12 전체 통과는 아니다.

다음 구현은 Google 요청/반환과 토큰 검증, 검증 식별자→사전 등록 활성 계정 연결, 세션 발급·현재 권한 재검사·폐기, 최초 관리자 준비 절차다. 이어서 계정 관리·수기 확인 UI/API, 업무 단위 배정·재배정과 역할별 조회를 구현한다. 03 예산 단계는 시작하지 않았다.
