# ERP 완성·실자료 입력·Notion 연계 통합 작업계획

2026-11-05 / Asia/Seoul. 현재 구현·참조 화면 검토·사용자 후속 요구를 합친 실행 기준이다. 이 문서는 계획이며 기능 완료나 업무 정책의 미결정 해소를 뜻하지 않는다.

2026-11-06 갱신: 생성된 [완성 예상 이미지](design/erp-dashboard-concept-2026-11-06.png)와 같은 형태로 구현하도록 사용자 지시를 반영했다. [이미지 기준 UI 명세](design/erp-ui-spec.md)가 P2~P7의 필수 화면·시각 검수 기준이다. 가상 데이터나 미결정 정책을 실제 기능으로 고정하는 근거는 아니다.

실행 방식 최종 정리: [자동 확인 규약](execution-checks.md)과 [단계 진행/최종 점검표](execution-progress.md)를 사용한다. 통합 P0~P7은 즉시 필수 통과 시 자동 계속하고 구현 순서가 끝난 뒤 F0 일괄 점검을 수행한다. 구현/단계 필수 통과와 최종 검증을 분리하며 F0 이전에 G1을 완료로 표시하지 않는다.

작업 실행 문구는 [단계별 프롬프트](completion-prompts.md), 향후 연계 계약은 [Notion 방향성](future-notion-integration.md)을 함께 사용한다. 기존 00~10 단계 번호를 없애거나 처음부터 재개발하지 않는다.

2026-11-06 실행 후속: 사용자가 통합 P0~P7 실행을 명시적으로 요청했고 EX-13~15/WF-01~04/ENV-02를 답변했다. 아래 ‘현재 기준선’은 실행 전 비교 기준으로 보존한다. 최신 구현/검수/차단은 [진행표](execution-progress.md)와 [STATUS](STATUS.md)를 따른다. P8/P9는 시작하지 않는다.

## 1. 이번 사용자 요구와 적용 순서

사용자가 정한 순서는 **ERP 구성 완료 → 실제 데이터 입력·대조 → Notion 예산사용내역·현황 연계로 실적 확인**이다. 이번 요청의 산출물은 현황 통합 검토와 작업용 프롬프트다. 이 요청만으로 앱 전 단계 구현·실자료 반영·외부 연계가 이미 수행되거나 운영 대상이 정해진 것은 아니다.

ERP 구성 완료에는 화면·업무 기능 외에 가상자료 전체 검수와 실제 자료를 안전하게 받을 실행 환경·백업 복구를 포함한다. 원본 자료의 자동 이관만이 입력 방법은 아니다. 사용자 입력과 승인 범위의 일괄 입력 중 필요한 방식을 P8에서 선택한다.

기존 로드맵은 09 실제 이관·시범 후 10 운영 준비였다. 사용자 순서를 지키기 위해 **09의 입력 도구 준비와 10의 환경/복구 준비를 실제 데이터 이전으로**, 실제 이관/입력·시범운영은 이후로 나눈다. 운영 최종 인수는 실제 데이터 대조 후 마무리한다.

## 3. 완료를 판정하는 세 기준

| 기준 | 통과 조건 | 다음으로 가능한 일 |
|---|---|---|
| G1 ERP 구성 완료 | 선택한 업무 범위와 필수 정책 확정, 04~07 기능·이미지 기준 UI 완성/비교 검수, 가상자료 권한/금액/파일/통합검수 통과, 운영대상에 맞는 환경·백업 복구·입력 도구 검증, 중대 결함 없음 | 실제 데이터 입력 준비/수행 |
| G2 실제 데이터 입력·대조 완료 | 원본/ERP의 건수·금액·상태·관계·첨부 대조, 기준일/기초잔액·중복 방지 확인, 담당자 확인과 제한 시범운영, 새 거래 처리 기준 확립 | Notion 실적 연계 착수 |
| G3 Notion 연계 완료 | 별도 대상/방향/필드/열람권한·실적 정의 확정 후 구현, ERP/외부 집계 일치, 지연/실패/재전송·권한 변경 검증 | 연계 운영 인수 |

G1에서 실제 데이터나 Notion 연계가 없다고 미완료로 보지 않는다. 반대로 제출·승인이 막힌 초안 화면만으로 G1 완료를 선언하지 않는다. 미결정 기능을 임의로 빼고 ‘전체 완료’로 표시하지 않는다. 제외할 업무는 사용자 선택과 제한을 기록한다.

P0~P7이 ERP 구성 완성 작업이다. 통합 실행 시 각 단계의 관련 기능/즉시 필수가 충족되면 별도 단계 승인 없이 계속한다. P7 준비 후 F0 최종 점검까지 포함해 G1을 판정한다. P8은 별도 실제 데이터 작업이고 P9는 그 이후다. 각 작업은 [실행 프롬프트](completion-prompts.md)의 해당 블록으로 시작한다. 단계 문서와 충돌하는 과거 문구는 BC/EX 최신 정책과 이번 실행 규약으로 정정한다.

### 생성 이미지로 확정한 화면 목표

P2~P7에서는 이미지를 직접 열어 보고 다음 구성을 유지한다. 새로운 대시보드 디자인으로 임의 변경하지 않는다.

- 흰 브랜드/사용자 헤더, 파란 상단 메뉴 **업무 관리 / 현황·보고서 / 설정**, 흰 좌측 그룹 메뉴, 작업 탭·경로.
- **사업연차·과제/비교과·기간 필터 → 요약 카드 4개 → 중간 2:1 예산표/처리할 업무 → 하단 전폭 최근 지출 신청표**의 순서.
- 카드: 현재예산 / 유효 신청 차감액 / 가용예산 / 실제 지급액. 표 합계·우측 숫자 정렬·파란 가용액·남색 패널 제목을 재현.
- 담당자 기준 이미지를 역할별 허용 범위에 맞게 적용하고 미구현 지표는 준비/미조회 상태로 구분. 이미지의 숫자·날짜·건수는 하드코딩하지 않음.
- 1600×1000px 데스크톱에서 기준 PNG와 비교하고 1280×800px·375×812px 및 네 역할/키보드 동작도 검증.

P2의 공통 틀과 P6의 실제 지표 연결을 구분하며 G1 시점에는 둘 모두 완성해야 한다. 각 단계는 변경 기본 검수, 전체 이미지/역할/뷰포트 대조는 F0에서 한 번 종합 수행한다. 상세 기준은 [UI 명세](design/erp-ui-spec.md)를 따른다. Notion 항목은 실제 데이터 입력·대조 이후 P9 전까지 추후 단계 안내다.

기존 확정 사항을 다시 묻지 않는다. 아래는 실제 미결정과 외부 환경 정보만 추린 목록이며 답변이 필요한 단계에서 묶어 확인한다. 명시적 답이 없는 기관 수치·조건을 개발자가 대신 정하지 않는다.

## 6. 유지할 금액·권한·자료 계약

- 단일 신청이며 제출 시 가용액 검사·차감을 원자적으로 처리한다. 초안은 미차감, 보완은 차감 유지, 적법한 복귀는 1회 복원 후 수정·재신청한다.
- 신청 한 건의 예산항목은 한 개다. 내부 승인·실청구·실제 지급은 별개 사실이며 승인·지급 시 다시 차감하지 않는다.
- 연구원 간 개별 업무·자료·집계는 비공개, 책임자는 담당 과제 조회 전용이다. 목록·직접 API·파일·보고서·미래 외부 실적에도 적용한다.
- 기관 로고·계좌/세금 필드·기관 결재 흐름은 참조 화면만 보고 도입하지 않는다. 현재 ERP 정책이 기준이다.
- 원 단위 정수와 불변 ID, 원 작성자·대행자·사유·버전·제출본·정정 사건을 보존한다. 지급/환입/순집행을 명확히 구분한다.
- 기존 Notion 배정자료 우선(BC-11~13)은 입력 기준에 관한 결정이다. 운영 중 금액을 Notion 수식으로 덮어쓰거나 ERP 변경을 원본에 되쓰는 근거가 아니다.
- 실제 계정·금액·증빙·키·DB·비공개 대조표는 공개 저장소에 넣지 않는다. 실자료 입력은 G1 이후 지정 환경에서만 수행한다.

## 7. 향후 Notion 때문에 지금 준비할 것

1. 과제·사업연차·예산항목·업무·초안·제출/집행건·지급/환입의 ID 연결과 출처를 추적한다. 현재 있는 ID/버전을 활용하며 표시명으로 매핑하지 않는다.
2. 화면·출력·미래 연계가 재사용할 서버 집계 정의를 만든다. 집계에 기준시각·필터·날짜 기준·조회 범위를 포함한다.
3. 최초/현재예산·유효 신청 차감액·가용액·실제 지급·환입·순집행의 의미를 분리한다. 전체 과제 예산과 연구원 개인 업무 실적의 열람 범위를 혼합하지 않는다.
4. 외부 서비스 실패가 ERP 금액 트랜잭션에 영향을 주지 않는 경계를 설계한다. 실제 외부 ID 매핑·전송/재시도·스케줄러는 P9에서 결정·구현한다.

권장 방향은 ERP의 검증된 실적을 권한이 제한된 별도 확인 영역에서 조회하는 것이다. 연계가 ERP→Notion 게시인지, ERP가 Notion을 조회·대조하는지, 수동/정기인지와 쓰기 대상은 아직 미확정이다. **기존 원본 Notion 읽기 전용 조건은 유지한다.** 현재 토큰·외부 DB·자동화·전송 작업은 만들지 않는다.

## 8. 작업 인수 방식

각 프롬프트 결과에는 실제 구현/즉시 검사/최종 이월 범위, 명령·실패/미실행, 관련 정책과 다음 진입 조건을 남긴다. 진행표·STATUS·CHANGELOG·history를 간결하게 갱신하고 전체 문서 일치화는 F0로 모은다. 유효한 증거를 재사용하되 관련 변경 뒤에는 영향 검사를 다시 실행한다. 최종 필수 미실행·실패·차단·낡은 증거가 남으면 G1 미완료다. 문서 작성만으로 앱 테스트나 G1/G2/G3 완료를 기록하지 않는다. 코드 반영·배포는 현재 지시 범위와 실제 원격 권한을 확인해 처리하고, 미커밋 변경을 자동 폐기하지 않는다.
