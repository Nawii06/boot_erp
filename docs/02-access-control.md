# 역할·접근권한 설계

4종 역할과 전체/배정 범위는 확정 요구다. 세부 파일 접근·계정 관리 기준은 D-04/D-05 미결정이며 02단계의 관련 구현 전에 확정한다. 01단계는 인증·권한 공통 경계만 구현했다. 아래 권한표 전체가 실제 구현·검수된 것은 아니다. [01 수행 후 점검사항](history/2026-10-05-phase-01-review.md) 참고.

과제책임자의 확인 여부는 청구 진행의 선행조건이 아니다. 관리자의 권한은 업무 절차·기록을 건너뛰는 별도 무기록 통로를 의미하지 않는다.

## 계정과 배정

- `users`: 로그인 주체, 역할, 활성 상태. 역할명과 연구원 직책/학생 여부를 동일시하지 않는다.
- `people`: 학생·교수·외부인 등 참여자 정보. 로그인 계정이 없어도 참여자로 등록 가능.
- `project_memberships`: 업무와 사용자/참여자 연결, 업무상 역할, 적용기간·활성 상태.
- 기본 제안은 계정당 시스템 역할 1개다. 여러 역할 겸임 필요 시 결정기록 후 명시적 유효 권한 계산을 설계한다.
- 배정 해제·계정 정지 즉시 새 요청을 차단하고 기존 기록의 작성자 식별정보는 유지한다.

## 본인 청구와 공동업무

작성자·신청자·현재 처리 연구원을 구분한다. 담당자가 대행 입력하면 실제 입력자와 대행 대상자를 함께 기록한다. 같은 프로젝트의 다른 연구원에게는 예산 합계/청구 요약만 제공하고 개인별 지급정보·증빙은 필요한 범위로 제한하는 것을 제안한다. 인수인계는 담당자의 명시적 재배정으로 처리한다.

과제책임자도 배정 업무의 현황·청구 요약을 조회하되, 개인 계좌·주민번호 등 불필요한 정보는 노출하지 않는다. 상세 증빙 접근 정책은 D-04에서 확정한다.

## 서버 검사 지점

목록, 상세, 검색, 자동완성, 집계, 엑셀/CSV, 파일 미리보기·다운로드, 임시 다운로드 URL 발급, 일괄작업을 각각 검사한다. 클라이언트가 보낸 프로젝트 ID·작성자 ID를 그대로 신뢰하지 않는다. 예산항목과 집행 건의 프로젝트가 같은지 서버/DB에서 검사한다.

업무 역할과 메뉴 숨김은 별개다. 읽기 전용 사용자가 직접 쓰기 API를 호출해도 거부해야 한다. 다른 사용자의 캐시·다운로드 결과를 재사용하지 않는다.

## 검수 연결

검수 A-01~A-05와 F-01~F-03을 사용한다. 관리자 우회 접근도 감사기록에 남긴다. 운영 DB 관리자 자체의 모든 행위를 애플리케이션만으로 막을 수 있다고 표현하지 않으며, 별도 운영 감사·백업으로 보완한다.
