# 02단계 로그인·계정·세션 정책

2026-10-05 후속 사용자 지시로 **S-01~S-10 권고안과 A-01~A-03 계정 운영 기준을 확정했다.** 현재 앱은 01단계의 미인증 경계이며 아래 Google 로그인·권한은 아직 구현하지 않았다. 최신 결정은 [AC-08~AC-11](07-decisions.md)이며 AC-01~AC-06은 유지한다.

## 확정된 사용자 정책

| 항목 | 확정 내용 |
|---|---|
| 로그인 | Google 연동 로그인. 향후 대학 SSO로 교체할 수 있는 구성 |
| 계정 관리 | 이메일 기준 관리, 담당자가 우선 수행하고 부재 시 관리자도 수행 가능 |
| 역할 | ERP 계정당 시스템 역할 1개 |
| 연구원 | 다른 연구원의 업무·자료가 서로 보이지 않음. 같은 과제 소속이라는 이유로 다른 연구원 자료를 공개하지 않음 |
| 과제책임자 | 담당한 과제·비교과의 내용 전체 조회. 기존 조회 전용·승인 단계 제외 유지 |
| 인수인계 | 재배정된 업무의 과거 자료·내용을 모두 승계하여 조회. 업무 연속성 유지 |

인수인계의 범위는 사용자 표현의 “동일한 업무와 내용”에 따라 **재배정된 업무에 속하는 전체 자료**로 해석한다. 전임자의 별도 미배정 업무나 다른 계정의 인증정보까지 넘기는 것은 아니다. 자료를 후임자 명의로 다시 작성하지 않고 원 작성자·검토자·시각을 보존한다. 후임의 수정·제출 가능 행위는 후임의 단일 역할과 업무 상태를 따른다. 책임자에게 쓰기 권한이 생기지 않는다. 전임자는 해제된 배정으로 접근할 수 없고, 담당자·관리자의 전역 업무 권한은 역할에 따라 별도로 평가한다.

## Google 로그인과 대학 SSO 교체를 위한 구현 방침

사용자에게 보이는 계정 등록·검색·관리 기준은 이메일로 한다. 데이터 참조는 불변 ERP 계정 ID에 연결하고, 인증 제공자별 식별자를 별도 연결한다. Google은 이메일 대신 안정적인 `sub`를 계정 식별에 사용하도록 안내한다. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)

- 인증 어댑터가 검증한 `issuer + subject`를 내부 계정 ID에 매핑한다. Google 이메일은 서버 검증 결과만 사용한다. 입력창·URL·헤더의 이메일 문자열만으로 인증하지 않는다.
- 이메일은 계정 관리 속성이다. 이메일 변경·계정 복구·대학 SSO 전환 시 동일인 확인을 거쳐 인증 연결을 변경하고 내부 계정·역할·업무·감사 이력은 유지한다. 이메일 일치만으로 기존 계정을 자동 병합하거나 다른 제공자 계정을 연결하지 않는다.
- ID 토큰의 서명·발급자·대상 client·만료와 로그인 요청의 state/nonce 등을 검증하는 라이브러리를 실제 구현 때 선정한다. Google의 비밀번호를 ERP가 수집·보관하지 않는다.
- Google 계정의 이메일이 Gmail/Google Workspace가 아닌 경우 `email_verified`만으로 현재 이메일 소유를 확정할 수 없는 경우가 있다. 해당 계정도 허용하되 최초 이메일 기반 연결·이메일 변경·복구 시 담당자가 소유를 수기로 확인하고 아래 확인 기록을 남긴다. [Google 서버 검증 안내](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- 초기 권한 요청은 로그인에 필요한 범위로 제한한다. Gmail·Drive·Notion·대학 ERP 자료 접근 권한은 요청하지 않는다. 이번 Google 인증 결정이 외부 업무자료 자동 연동을 허용하는 것은 아니다.
- ERP의 세션·역할·배정 검사는 제공자와 분리한다. 대학 SSO의 프로토콜·식별자·로그아웃 기능은 아직 알려지지 않았으므로 OIDC라고 단정하지 않는다. 해당 사양에 맞는 어댑터와 검증된 계정 연결 절차를 추가하고 전환 검수 후 교체한다.

## 확정된 세션·복구 정책

세션은 Google 인증 후 **ERP에서 로그인 상태를 유지하는 단위**다. Google 로그인 상태와 ERP 세션은 별개이므로 ERP가 시간을 정하고 서버에서 만료·폐기해야 한다. 유휴 시간과 최대 유지 시간을 함께 두는 근거는 [OWASP 세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)다. 아래 수치·동시 접속 수는 사용자가 채택한 프로젝트 기준이며 법정 기준이라는 의미는 아니다.

| 번호 | 항목 | 확정 기준 | 적용 의미 |
|---|---|---|---|
| S-01 | 미사용 자동 로그아웃 | 마지막 사용자 활동 후 **15분** | 백그라운드 조회만으로 시간을 계속 연장하지 않음 |
| S-02 | 최대 로그인 시간 | 로그인 시점부터 **8시간** | 계속 사용해도 재로그인 필요 |
| S-03 | 만료 전 안내 | **2분 전** 경고, 만료 전 사용자 활동으로 유휴 시간 연장 가능 | 입력 손실을 줄임. 최대 8시간은 연장하지 않음. 저장된 임시자료는 재인증 후 재권한 검사하여 복원하는 방향 |
| S-04 | 장기 로그인 유지 | “로그인 상태 유지” 기능 **미제공** | 공용 PC 잔류 위험 축소. 창 닫기만으로 서버 로그아웃이 보장된다고 간주하지 않음 |
| S-05 | 동시 접속 | 계정당 **2개 브라우저/기기 세션**, 초과 신규 접속 거부 후 기존 세션 종료 안내 | PC·보조 기기 사용 허용. 같은 브라우저의 여러 탭은 한 세션 |
| S-06 | 로그아웃 | 현재 ERP 세션 종료 + 본인의 “전체 기기 로그아웃” 제공 | ERP 세션만 폐기. Google/Gmail까지 로그아웃된다고 표시하지 않음 |
| S-07 | 계정 보안 변경 | 정지 시 전체 ERP 세션 폐기, 역할·인증 이메일/연결 변경 시 기존 세션 폐기 후 재로그인 | 정지·배정 해제 즉시 새 접근 차단도 유지 |
| S-08 | 민감 계정관리 작업 | 역할·인증 연결 변경/복구 전에 **최근 5분 이내 추가 본인 확인** | Google 로그인 재진입이 비밀번호/MFA 재입력을 항상 보장하는 것은 아니므로 제공자 기능을 검증한 후 수단 선정. 추가 확인의 주체는 작업 수행자이며 복구 대상의 동일인 확인은 별도 수행 |
| S-09 | Google 계정 분실 | Google의 계정 복구 절차 사용, 담당자는 필요 시 ERP 접근 정지 | ERP에서 Google 비밀번호를 초기화할 수 없음. 본인확인 없이 새 이메일로 바꿔주지 않음 |
| S-10 | 이메일 변경·SSO 전환·ERP 복구 | 일반 계정은 담당자가 동일인 확인 후 계정 연결 변경, 부재 시 관리자 대행, 전후·사유·행위자 감사 | 예전 세션 폐기와 업무 ID 보존. 관리자 계정의 변경·복구는 A-02에 따라 관리자만 수행 |

서버에서 폐기 가능한 세션 저장소와 HttpOnly 쿠키, 운영 HTTPS의 Secure 속성, 요청 위조 방어를 사용하는 방향으로 구성한다. 세션 토큰·비밀번호·실제 자료를 로그나 브라우저 영구 저장소에 남기지 않는다. Google 장애 시 우회 비밀번호를 자동 제공하지 않으며 재로그인은 장애 해소 후 가능하게 한다. 장애 중 이미 발급된 ERP 세션을 즉시 끊을지 여부는 운영 대응 정책으로 별도 결정한다.

## 확정된 계정 운영 경계

| 번호 | 항목 | 확정 기준 |
|---|---|---|
| A-01 | 가입 허용 | **담당자/관리자가 사전 등록한 이메일만 로그인 허용**. 미등록 이메일에 자동 계정·역할·업무를 부여하지 않음 |
| A-02 | 관리자 계정 관리 | **관리자 계정 관리와 관리자 역할 부여·회수는 관리자만 수행**. 담당자가 자신 또는 다른 계정을 관리자로 승격하거나 기존 관리자 계정을 정지·변경·복구할 수 없음 |
| A-03 | 허용 Google 계정의 범위 | **다른 이메일로 만든 Google 계정도 허용**. 해당 이메일의 소유는 **담당자가 수기로 확인**. 일반 계정은 기존 대행 원칙에 따라 부재 시 관리자가 수행 가능. 관리자 계정의 확인·관리 처리는 A-02에 따라 관리자만 수행 |

### 수기 이메일 소유 확인의 구현 방침

사전 등록과 이메일 소유 확인 완료를 별도 상태로 관리한다. 대상 이메일을 실제 사용할 수 있음을 담당자가 수동으로 확인하고, 대상 내부 계정/이메일·확인자·확인 시각·확인 방법·결과를 비공개 감사기록에 남긴다. 단순한 명단 일치나 사전 등록만으로 소유 확인을 완료 처리하지 않는다. 자동 이메일 발송·외부 메일 연동을 구현하는 결정은 아니다.

확인 대기·실패 상태에서는 ERP 로그인 세션을 발급하지 않는다. 수기 확인은 해당 이메일에만 적용하고 이메일 변경·인증 연결 복구 시 다시 확인한다. Google 토큰 검증과 사전 등록·계정 활성 여부 검사도 함께 통과해야 한다. 확인 기록을 수정할 때 원 기록을 덮어쓰지 않고 정정 이력을 추가하며, 운영 이메일·확인 자료는 공개 저장소에 저장하지 않는다.

담당자의 우선 수행과 관리자의 대행 가능은 확정이다. 부재 감지 시스템이나 관리자의 정상 시점 접근 차단은 사용자 지시에 없는 추가 기능이므로 도입하지 않는다. 담당자 계정 관리 메뉴와 관리자 전용 인증 제공자/client secret/서버 설정은 분리한다.

실제 연결 시험 전에는 프로젝트용 Google OAuth client, 허용 origin/redirect URI, 시험 사용자 범위와 자격증명의 비공개 주입이 필요하다. 현재 생성·접속·비밀정보 제공을 완료한 상태가 아니다. 비밀번호·client secret을 대화나 공개 저장소로 받지 않는다. 최초 관리자 준비 및 모든 관리자 접근을 잃은 경우의 복구 절차는 운영 준비 때 문서화한다. 이 경우에도 담당자에게 관리자 관리 권한을 자동 부여하지 않는다.

## 02단계 구현 시 검수할 경계

- 연구원 A/B를 같은 과제에 배정해도 서로의 업무 이름·목록·상세·증빙·검색 결과·집계/출력에서 타인 업무를 노출하지 않는지 확인한다. 프로젝트 배정만 검사하는 01 공통 함수를 완성된 연구원 권한으로 사용하지 않는다.
- 책임자는 담당 과제·비교과의 청구/증빙/지급자료까지 조회하고, 비담당 업무 접근과 모든 업무 쓰기는 거부되어야 한다. 해당 범위의 “전체 자료”에 인증 비밀이나 서버 운영 설정은 포함되지 않는다.
- 재배정 후 후임은 같은 업무 ID의 전체 과거 자료를 조회한다. 원 작성자·전임자 감사기록은 유지하고, 미이관 업무로 범위를 넓히지 않는다.
- 계정당 역할은 하나이며 Google/대학 SSO 연결이 추가되어도 별도 역할을 합산하지 않는다. 이메일 변경·로그인 제공자 전환으로 업무 참조가 끊기지 않는지 확인한다.
- 확정된 S/A 항목으로 세션·계정 복구·관리 권한을 검수한다. 미등록 이메일, 수기 확인 대기/실패, 이메일 변경 후 과거 확인 재사용, 담당자의 관리자 계정 변경은 거부되어야 한다. 이번 문서 작성은 이 기능들의 구현 또는 검수 통과를 의미하지 않는다.
