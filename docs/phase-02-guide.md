# 02단계 사용·인수인계

2026-10-18. 구현 범위는 계정·세션·과제/비교과·업무 배정과 인수인계다. 예산·청구·지급·증빙 업로드는 후속 단계다. 실제 Google 로그인과 ERP 인증 앱 확인까지 대조하여 02를 완료했다. [최종 인수인계](history/2026-10-18-phase-02-complete.md)와 [진행상황](STATUS.md)을 따른다.

## 7개 순서와 사용 방법

| 순서 | 구현 내용 | 사용 방법 |
|---|---|---|
| 1 로그인 | Google 코드 교환·서명/발급자/대상/만료/nonce 검증, PKCE·일회성 브라우저 연결 state, 최초 관리자 등록 | `http://localhost:3000`에서 Google 계정으로 로그인 |
| 2 세션 | 유휴 15분/최대 8시간, 2분 전 경고, 동시 2개, 현재/전체 로그아웃 | 3번째 접속은 거부. 기존 기기에서 전체 로그아웃 후 다시 로그인 |
| 3 계정·복구 | 사전 등록 → 수기 소유 확인 → 활성화, 단일 역할, 관리자 전용 관리자 계정 관리 | 계정 관리 전 추가 본인 확인. 변경 사유 필수. 이메일 변경/복구는 정지·재확인 후 활성화 |
| 4 과제·비교과 | 관리 코드·이름·유형·사업연차 기준연도, 참여자 배정/해제 | 담당자/관리자가 과제 등록 후 참여자를 배정 |
| 5 업무 권한 | 업무별 담당 연구원, 책임자의 담당 과제 전체 조회, 서버 공통 조회 조건 | 연구원은 자신의 업무만 조회. 책임자는 조회 전용. 일반 파일 경로는 미개방 |
| 6 인수인계 | 동일 업무의 담당 연구원 변경, 내용·작성자·사유·이력 보존 | 후임을 먼저 과제 참여자로 등록한 뒤 업무 수정·재배정. 전임은 해당 업무 접근 불가 |
| 7 검수 | 실제 DB/HTTP·브라우저·Google 연결과 기록 확인 | [검수 결과](history/2026-10-18-phase-02-access.md) 및 [검수표](06-acceptance.md) |

목록·검색·내려받기·통계는 동일한 업무 권한을 사용한다. 현재 목록은 최대 1,000건이며 화면 건수는 조회된 범위의 건수다. 내려받기는 JSON이고, 후속 보고서/CSV 기능을 대신하지 않는다. 이름이나 제목을 숨겨도 상세 주소를 알면 열리는 구조를 허용하지 않는다. 미래의 실제 파일·청구·지급 경로는 해당 단계에서 같은 권한을 적용하고 재검수한다.

## 추가 본인 확인

담당자와 관리자의 민감 계정 관리에는 인증 앱(TOTP) 코드가 필요하다. Google의 계정 선택 화면만으로 최근 5분 이내 추가 본인 확인을 완료 처리하지 않는다.

1. Google 로그인 후 5분 이내에 **추가 본인 확인 → 인증 앱 등록 키 보기**를 선택한다.
2. 인증 앱의 수동 설정 키 등록에서 해당 키를 등록한다. 시간 기반, 6자리, 30초 기준이다.
3. 인증 앱의 현재 코드를 ERP에 입력하고 **코드 확인**을 누른다. 등록 완료 후 키는 다시 표시하지 않는다.
4. 계정 관리 전 코드 확인 결과는 5분간 유효하다. 같은 코드는 재사용할 수 없다. 실패 5회 시 15분 동안 코드 확인을 제한한다.

최초 등록 도중 Google 로그인 후 5분이 지나면 등록 시간 만료 안내와 **Google로 다시 로그인** 버튼이 표시된다. 버튼으로 로그인한 뒤 5분 이내에 등록 키 보기와 코드 확인까지 마친다. 단순 새로고침이나 **계속 사용**은 최초 등록 시간을 갱신하지 않는다. 이번 안내 수정 전의 일반 권한 오류가 계속 보이면 화면을 새로고침한다.

등록 키와 코드를 대화·공개 문서·로그에 복사하지 않는다. 키는 DB에 AES-256-GCM으로 암호화하며 별도 서버 키는 저장소 밖에 둔다. 관리자 계정은 관리자만 복구한다. 일반 계정은 담당자가 본인을 확인하고 복구하며 관리자가 대행할 수 있다. 복구 시 기존 연결·세션·인증 앱을 폐기하고 수기 확인부터 다시 진행한다.

## 실행과 최초 관리자

Google Console 등록과 비공개 JSON 준비는 [Google 연결 안내](google-login-setup.md)를 따른다. 아래는 가짜 경로다. 실제 값은 공개 저장소에 넣지 않는다.

```powershell
.\scripts\app.cmd run init:auth-key
.\scripts\app.cmd run local -- migrate
.\scripts\app.cmd run local -- migrate:test
$env:BOOT_ERP_ADMIN_FILE = 'C:\boot_erp_private\admin.json'
.\scripts\app.cmd run local -- bootstrap-admin
$env:BOOT_ERP_GOOGLE_OAUTH_FILE = 'C:\boot_erp_private\google-oauth.json'
.\scripts\app.cmd run build
.\scripts\app.cmd run local -- start --port 3000
```

관리자 파일은 [가상 양식](examples/admin-bootstrap.example.json)에 맞춘 UTF-8 JSON이다. 실제 소유 확인 후 `ownershipConfirmed`를 true로 지정한다. 최초 등록은 기존 관리자 부재 시에만 동작하고 동일 이메일의 재실행은 변경하지 않는다. 웹을 통한 최초 관리자 자동 승격은 없다. Google 시험 사용자 등록만으로 ERP 관리자 권한이 생기지 않는다.

서버 암호화 키는 `%LOCALAPPDATA%/boot_erp/auth/encryption.key`에 최초 1회 생성되며 기존 키를 덮어쓰지 않는다. 새 PC/복구 시 DB와 함께 승인된 비공개 방식으로 보존해야 한다. 키를 잃으면 기존 인증 앱 비밀값을 해독할 수 없다. 운영의 키 보관·백업·HTTPS·도메인은 10단계에서 검증한다.

## 모든 관리자 접근을 잃었을 때

가능하면 다른 관리자가 화면에서 복구한다. 마지막 활성 관리자를 일반 관리 화면에서 정지/강등하는 작업은 거부한다. 모든 관리자 접근을 잃은 경우 서버 운영자가 본인을 별도로 확인한 후 로컬 명령으로 기존 관리자만 복구한다. 담당자에게 관리자 권한을 주지 않는다.

비공개 관리자 JSON에 `existingEmail`(기존 관리자 이메일), `reason`(복구 사유), `operatorName`(실제 서버 작업자)을 추가하고, `email`·`name`·`ownershipMethod`·`ownershipConfirmed`를 확인한 뒤 `scripts/app.cmd run local -- recover-admin`을 실행한다. 기존 내부 ID를 보존하고 이전 연결·세션·인증 앱을 폐기하며 수기 확인·복구 작업자·사유를 기록한다. 새 이메일로 Google 로그인 후 인증 앱을 다시 등록한다. 이 명령은 이번 실제 관리자에게 실행하지 않았다. 운영 장애 복구 연습은 10단계에서 별도 수행한다.

## 검수 명령과 경계

```powershell
.\scripts\app.cmd test
.\scripts\app.cmd run typecheck
.\scripts\app.cmd run local -- test:db
.\scripts\app.cmd run build
# localhost:3000이 비어 있을 때만 실행 (설치된 Microsoft Edge 사용)
.\scripts\app.cmd run local -- test:ui
# 실제 앱 실행 중 별도 터미널
.\scripts\app.cmd run test:http
.\scripts\app.cmd run check:docs
```

DB 시험은 임의의 전용 스키마를 만들고 명시적 객체 순서로 정리한다. UI 시험은 그 스키마만 사용하는 별도 앱과 임시 Edge 프로필을 사용하며 가상 자료만 캡처한다. 사용자 로그인 세션을 가상 검수에 사용하지 않는다. 기존 서버가 3000을 사용 중이면 UI 시험을 거부한다. 브라우저의 GET 상태 조회는 유휴 시간을 연장하지 않고 실제 사용자의 입력·계속 사용 동작만 연장한다.

실제 대학 SSO는 연결하지 않았다. 가상 제공자 교체 검수로 내부 계정·업무 이력 보존을 확인했다. Notion 원본 변경·외부 업무자료 자동 연동·03단계 구현·운영 배포는 이번 범위가 아니다.
