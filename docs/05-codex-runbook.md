# VS Code에서 Codex로 단계별 작업하기

## 1. 준비

1. 로컬 PC에 Git과 VS Code를 준비한다.
2. VS Code에서 OpenAI가 제공하는 Codex 확장을 설치하고 본인 계정으로 로그인한다.
3. 아래 명령으로 저장소를 가져온다. 기존 복제본이 있으면 새로 복제하지 않고 해당 폴더를 연다.

```bash
git clone https://github.com/Nawii06/boot_erp.git
cd boot_erp
code .
```

`code` 명령이 없으면 VS Code의 폴더 열기로 `boot_erp`를 선택한다. GitHub 저장소 쓰기 인증과 Codex 로그인은 별도로 확인한다. 이 문서는 로컬 설치·인증 완료를 보증하지 않는다.

확장 사이드바에서 Codex를 연다. 공식 안내상 VS Code에서는 Codex 아이콘 또는 명령 팔레트의 `Codex: Open Codex Sidebar`를 사용할 수 있다. 확장은 편집기 문맥을 활용하며, `AGENTS.md`는 프로젝트 작업 지침을 전달하는 파일이다.

근거: [Codex IDE 공식 안내](https://learn.chatgpt.com/docs/codex/ide), [AGENTS.md 공식 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md). 확인일 2026-10-04. 설치 UI·기능은 공식 문서를 다시 확인한다.

## 2. 첫 작업 프롬프트

```text
이 저장소의 AGENTS.md, docs/STATUS.md, docs/01-requirements.md,
docs/07-decisions.md와 docs/stages/00-discovery.md를 읽고 00단계만 수행하라.

목표는 실제 로컬 개발환경 점검과 다음 구현을 위한 정책·기술 결정 정리다.
기존 파일과 작업 중 변경을 보존하고, 아직 애플리케이션 전체를 만들지 마라.
사용자 확정 요구, 설계 제안, 확인이 필요한 사실을 구분하라.
내부 PDF나 실제 청구·개인정보를 공개 저장소에 올리지 마라.
Notion은 수정하지 말고 외부 연동도 구현하지 마라.
환경 점검과 확정 가능한 설계는 진행하고, 외부기관 정책 등 알 수 없는 사항만 묶어서 질문하라.
작업 후 STATUS, 결정기록, CHANGELOG와 단계 작업기록을 갱신하라.
변경 파일, 검수 결과, 미결정, 다음 작업을 보고하라.
```

## 3. 단계별 실행

각 단계 파일의 프롬프트를 사용한다. 해당 단계 외 기능을 자동으로 이어서 만들지 않는다. 이미 사용자가 정한 사항을 다시 승인받으려 하지 않는다. 미결정이 있어도 관련 없는 문서·가상 데이터 검증은 진행할 수 있다.

1. `git status --short`로 작업 중 변경을 확인한다.
2. 선행 단계의 완료 증거와 미결정을 확인한다.
3. 새로운 기능 작업은 `codex/phase-NN-short-name` 형태의 브랜치에서 진행한다.
4. 해당 단계의 기능과 검수를 수행한다.
5. 결과 문서·상태·연혁을 갱신하고 diff를 확인한다.
6. 공개할 수 있는 파일만 커밋·푸시한다. 원격 인증 실패는 성공으로 보고하지 않는다.
7. 필요하면 PR로 검토하고 기본 브랜치에 반영한다. 다음 단계는 반영된 기준에서 시작한다.

예시(실제 현재 브랜치·변경사항을 확인한 뒤 실행):

```bash
git status --short
git switch main
git pull --ff-only
git switch -c codex/phase-01-foundation
```

미커밋 변경이 있으면 `git switch`나 재설정을 강행하지 않는다. 각 단계 파일은 예정 작업이며 명령 실행·배포 권한을 자동 확대하지 않는다.

## 4. 이어서 작업하는 프롬프트

```text
AGENTS.md와 docs/STATUS.md, 가장 최근 docs/history 기록을 읽어 현재 상태를 확인하라.
내가 지정한 단계는 NN단계다. 해당 단계 파일과 선행 검수 결과를 확인하라.
이미 완료된 기능을 다시 만들지 말고 미완료 항목부터 진행하라.
문서상의 완료 표시만 신뢰하지 말고 관련 코드·검수 증거와 대조하라.
새로운 사용자 결정은 docs/07-decisions.md에 날짜·영향과 함께 남겨라.
이전 대화에 없는 사실을 추정하여 정책으로 확정하지 마라.
```

## 5. 검토만 요청하는 프롬프트

```text
이번 단계의 diff와 docs/06-acceptance.md를 기준으로 검토하라.
요구 누락, 미배정 업무·파일 접근, 예산 이중 차감, 상태 전이 오류,
공식 ERP 처리와 내부 상태 혼동, 민감자료 공개 여부를 확인하라.
변경이 필요하면 원인·영향·수정 범위를 제시하고 현재 요청이 검토만이면 파일을 수정하지 마라.
실행하지 않은 테스트는 미실행으로 표시하라.
```

## 6. 단계 완료 보고 양식

- 단계/범위, 사용자 관점에서 바뀐 동작
- 변경 파일, 관련 요구사항 ID
- 실제 실행한 명령과 결과, 실패·미실행 사유
- 남은 결정·제한·운영 위험
- 커밋/브랜치/PR(있을 때만 실제 값)
- 다음 단계 진입 가능 여부와 다음 작업

기본적으로 모든 구현을 한 번에 요청하지 않는다. 00단계에서 기술을 정하고, 01단계가 실제 실행 명령을 확립한 후 이후 단계에서 같은 명령을 사용한다. 개발 중의 가상 계정·가상 자료를 운영 인증으로 오인하지 않는다.
