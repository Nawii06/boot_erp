# 예산 신청·변경·분류 정책

기준일: 2026-10-18. 사용자의 D-02/D-03/D-07 및 준비 마무리 답변에 따른 확정 정책과 설계 해석이다. [결정기록](07-decisions.md)의 BC-01~BC-10을 따른다. 정책·분류코드 구성과 Notion 읽기 전용 배정자료 검토를 수행했으며 03 기능·DB 반영은 미수행이다.

## 신청 즉시 차감 — D-02

- 기본 예산에서 지출 신청 금액만큼 사용 가능 잔액을 즉시 차감한다. 내부검토 완료까지 차감을 미루지 않는다.
- 다음 신청은 이미 차감된 잔액 범위에서만 가능하다. 잔액 부족이면 신청과 차감 모두 실패해야 한다.
- 사전 예산·사후 청구의 별도 절차를 두지 않는다. 작성 중 초안은 신청 전이며 차감하지 않는다.
- 신청 건이 신청 이전 단계로 돌아가면 해당 신청의 차감을 취소하여 잔액을 복원한다. 재신청은 그 시점 잔액을 다시 검사한다.
- 사용자 표현의 차감 “삭제”는 차감 효력 제거로 구현한다. 원 신청·취소 사건과 행위자·사유를 보존하며 원장을 물리 삭제하지 않는다.
- 기본 예산 자체를 매번 덮어쓰지 않는다. 현재예산과 신청별 유효 차감액을 분리하여 잔액을 계산한다.
- 이 차감은 지출 신청에 적용한다. 항목 간 예산변경 신청 자체를 지출로 계산하지 않는다.

가용액 = 현재예산 - 유효한 신청 차감액 합계. 신청 승인·실제 지급을 별도 기록하더라도 같은 금액을 다시 차감하지 않는다. 실제 지급 여부는 신청이나 담당자 승인만으로 추정하지 않는다.

가상 예: 예산 1,000만원 → 100만원 신청 성공 시 900만원 → 다음 950만원 신청은 거부 → 첫 신청을 신청 전으로 되돌리면 1,000만원 → 90만원 재신청 시 910만원. 동일 요청 재시도는 차감·복원 각각 한 번만 반영한다.

신청·잔액 검사·차감·감사는 같은 DB 트랜잭션으로 처리한다. 동시 요청, 오래된 버전, 중복 클릭에서도 잔액이 음수가 되지 않도록 한다. 기존 코드의 예약 용어는 마이그레이션 시 이 의미로 정리하며 별도 사전예약 업무를 유지하지 않는다.

## 회수·보완·취소·금액 수정

2026-10-18 사용자 후속 답변으로 확정했다. 아래는 지출 신청의 처리이며 예산변경 신청 자체를 지출 차감으로 계산하지 않는다.

| 행위 | 권한·조건 | 상태·예산 효과 |
|---|---|---|
| 연구원 회수 | 본인 신청, 담당자 처리 시작 전 | 신청 전으로 복귀·차감 복원, 수정 후 재신청 가능 |
| 보완 요청 | 담당자 | 신청 효력을 유지하고 상태만 보완으로 변경. 차감 유지 |
| 보완 제출 | 본인 신청의 보완 허용 내용 | 금액이 같으면 기존 차감 유지, 추가 차감 없음 |
| 반려·취소 | 담당자 또는 관리자 업무 처리 권한. 연구원은 위 회수 조건 적용 | 차감 복원, 사유·원 신청 버전 보존, 수정 후 재신청 허용 |
| 승인 후 취소 | 지급 전, 담당자 또는 관리자만 | 승인 효력 취소·차감 복원·이력 보존. 수정 후 재신청·재검토 |
| 금액 수정 | 먼저 적법한 회수·취소로 신청 전 단계 복귀 | 기존 차감 복원 → 금액 수정 → 재신청 시 현재 잔액 검사·새 금액 차감 |

보완 상태는 신청 전 단계가 아니다. 보완을 이유로 잔액을 복원하지 않으며 금액 변경이 필요하면 별도의 복귀 절차를 거친다. 처리 시작 이후 연구원이 보완 상태를 이용해 스스로 회수하거나 금액을 직접 덮어쓰지 못하게 한다.

구현 기준: 담당자 처리 시작을 서버의 상태·시각·행위자 기록으로 식별한다. 단순 상세 열람만으로 처리 시작을 추정하지 않는다. 회수와 처리 시작이 동시에 요청되면 상태·버전 잠금으로 하나만 성공한다. 지급 전 여부도 서버에서 검사한다. 부분 지급이 발생한 건도 일반 취소로 자동 복원하지 않으며 지급 후 정정·환입은 별도 정책을 따른다.

예: 100만원 신청 → 적법한 복귀로 100만원 복원 → 120만원으로 수정 → 재신청 시 잔액이 120만원 이상이면 차감, 부족하면 신청 전 상태 유지. 기존 100만원 신청이 자동으로 다시 살아나지는 않는다.

## 연구원 예산변경 — D-03

| 항목 | 확정 기준 |
|---|---|
| 연구원 신청 범위 | 본인이 담당하는 과제 전체의 예산항목 |
| 과제 내 비목·세목 이동 | 허용. 변경행 합계 0, 같은 과제 여부 검사 |
| 과제 간 이동 | 연구원에게 불허 |
| 총예산 증액·감액 | 연구원 불허. 담당자만 수행 |
| 내부 검토 | 담당자 |
| 변경 최종 확정 | 담당자, 관리자 대행 가능 |
| 필수 자료 | 변경 사유, 변경 전·후 금액, 첨부자료 |
| 감액 한계 | 기존 신청 차감·지급을 침해하는 감액 차단. 관련 건 정정·취소가 선행 |
| 외부 공식 승인 | 이 내부 ERP에서 관리하지 않음. 담당자 승인(허용된 관리자 대행 포함)을 시스템 승인 완료로 취급 |

총예산 증감의 수행 권한은 사용자의 “담당자만”을 적용하고, 관리자의 최종 확정 대행을 총액 증감 직접 수행 권한으로 확대하지 않는다. 과제책임자는 계속 조회 전용이다. 변경신청·다중 변경행·확정·감사를 원자적으로 처리하고 확정 이력은 덮어쓰지 않는다.

담당 과제 전체의 예산변경에 필요한 예산항목·금액 접근과 다른 연구원의 개별 업무·청구·증빙 열람은 구분한다. 타 연구원 자료 비공개 정책은 유지한다. 공통 잔액 표시 범위는 구현 시 최소 필요 정보로 제한한다.

외부 공식 승인 상태·문서번호를 변경 확정의 필수 조건으로 만들지 않는다. 이는 내부 시스템의 승인 정의이며 대학의 실제 승인·실제 지급을 수행했다는 증거로 기록하지 않는다.

기존 별도 양식은 첨부파일로만 받는다. 변경 사유·전후 금액은 시스템의 필수 입력으로 유지하고 양식 내부를 자동 추출하거나 양식을 웹 화면으로 재현하지 않는다. 실사용 후 필요에 따라 변경한다. 첨부의 필수 여부·비공개 저장·버전·다운로드 권한 검수는 유지하며 실제 양식 파일을 받기 전에는 필드나 확장자를 확인했다고 기록하지 않는다.

## 분류·코드 — D-07

- 분류는 비목 → 세목 → 세세목의 3단계다. 과제와 비교과에 동일 분류체계를 사용한다.
- 사용자 지정 PDF의 “수정 후” 예산항목 좌·우 열을 비목·세목으로, 세부내용의 개별 금액 행을 세세목으로 매핑했다. 수정 전 항목을 현행 목록에 혼합하지 않는다.
- 여러 용도가 한 금액으로 묶인 원문 행은 하나의 세세목으로 보존한다. 산출 횟수·인원·과제 수는 설명으로 보존하며 같은 금액을 다시 곱하지 않는다.
- PDF의 산출 단가는 이 문서의 예산 근거이며 모든 업무에 적용할 보편적 법정 단가로 확정하지 않는다.
- 코드 형식은 비목 `B01`, 세목 `B01.01`, 세세목 `B01.01.001`이다. 각 단계 순번은 2/2/3자리로 부여한다. 원문에서 확인된 대학 공식 코드가 아니라 사용자 지시에 따라 구성한 ERP 내부 관리코드다.
- 최초 코드 발급 뒤에는 재사용하지 않는다. 이름·상하위 분류 변경은 내부 고유 ID, 코드, 버전·적용일·변경 전후·사유를 보존하고 관리한다. 코드 숫자에서 현재 부모 관계를 추정하지 않는다.
- 담당자·관리자가 분류를 추가·변경하고 승인한다. 외부 승인 절차를 추가하지 않는다. 사용된 분류는 삭제 대신 비활성화하며 과거 예산·신청의 당시 버전을 보존한다.
- 실제 금액·원문 매핑은 Git 제외된 로컬 참고 파일로만 작성했다. 공개 저장소에는 원문·실제 예산·개인정보를 넣지 않는다. DB seed에는 가상 값만 사용한다.

## Notion 예산 배정 참고 구조

사용자 지정 페이지의 프로젝트·예산배정 데이터를 읽기 전용 조회했다. 원본 DB·페이지·값·뷰·댓글·자동화는 변경하지 않았다. 상세 이름·금액·원본 URL·관계 ID는 비공개 로컬 검토표에만 보존한다.

- 프로젝트의 구분으로 산공과제·비교과를 나누고, 예산배정 행의 프로젝트 관계로 항목과 배정액을 연결한다. 제목의 사람 이름을 계정·권한으로 자동 변환하지 않는다.
- 조회 범위에서 유효 프로젝트 13개(산공 6, 비교과 7)와 배정 73건을 확인했다. 이름·구분 없는 프로젝트 1행은 사용 대상에서 제외하고 원본을 그대로 둔다.
- Notion 배정금액은 조회 시점의 참고값이다. 최초 편성액인지 변경반영 현재액인지는 단정하지 않으며 승인된 변경요청의 차액을 자동으로 다시 더하지 않는다.
- 배정금액 합계는 가용잔액이나 지급액이 아니다. Notion 사용확정/롤업 계산을 새 ERP의 신청 즉시 차감 정책으로 그대로 이식하지 않는다.
- PDF는 기존 분류·코드 기준, Notion은 실제 프로젝트·배정 구조 참고다. 두 자료의 적용 범위·시점 관계와 일부 세세목 연결이 불명확하므로 금액을 합산하거나 강제로 맞추지 않는다.
- 프로젝트·배정 날짜에 빈 값이 있고 완전한 적용 기간이 없다. 활동일·작성일을 예산 사용기간으로 추정하지 않는다.

## 남은 세부사항과 다음 작업

확정된 정책을 다시 승인받지 않는다. 다음 사항은 아직 구체적으로 정해지지 않았으며 관련 기능 구현 전에 필요한 범위만 확인한다.

1. 실제 배분 자료는 Notion에서 확인했다. 실자료 입력 전에는 적용 사업연차·기간, PDF와 Notion 금액의 기준 범위, 명확하지 않은 세세목 매핑을 확인한다. 전체 배분 자료를 다시 요구하거나 균등 배분하지 않는다.
2. 회수·보완·반려·취소·금액 수정·첨부 운영은 위 정책으로 확정됐다. 지급 후 정정·환입 및 추가/분할 신청은 후속 정책으로 남는다.
3. 연구원 예산변경 첨부는 03 구현에서 비공개 저장·권한 검수를 포함한다. 양식 원본 미제공은 일반 첨부 기능 구현의 차단 사유가 아니며 원문 재현·자동 추출은 하지 않는다.

따라서 가상 자료로 03 기능 구현을 진행할 기준은 확보했다. 실제 자료 입력은 위 대조 사항을 해결한 뒤 별도로 수행한다.

다음은 03 예산배정·변경·금액 서비스 구현이다. 04/05의 종전 사전신청·사후청구 초안은 이 단일 신청 정책에 맞춰 구현 전에 다시 정리한다. D-07의 나머지 유형별 증빙·단가·기한, D-08/D-09 등 미답변 정책은 그대로 남는다.
