# 역할별 화면과 대표 업무 여정

2026-10-04 / 00단계 합의용 초안. 화면은 구현되지 않았다. 역할·배정 범위는 확정 요구이며 메뉴 구성·상태 명칭·상세 권한은 제안이다. 근거: [요구사항](01-requirements.md), [권한표](02-access-control.md), [업무 흐름](03-data-and-workflows.md).

공통 화면은 검색·필터, 제출 버전, 처리이력, 오류/권한 없음, 증빙 누락·보완 안내를 제공하는 안이다. 메뉴를 숨기는 것으로 권한 검사를 대신하지 않는다. 상세 API·파일·검색·통계·내보내기에도 같은 업무 배정 검사를 적용한다. 과제책임자에게 승인·제출 버튼을 두지 않는다.

## 대표 여정: 가상 집행 건 1개

실제 개인·청구·계좌를 사용하지 않는다. 다음 순서와 금액은 합의용 예시이며 기관의 승인 규정으로 간주하지 않는다.

1. 연구원은 로그인 후 배정 업무를 선택하고 예산·가용액을 조회한다. 타 업무의 URL·파일에 직접 접근해도 거부해야 한다(A-01).
2. 같은 집행 건 ID 아래 1,000,000원 사전신청을 작성·제출한다. 담당자가 보완을 요청하면 기존 제출본을 남기고 재제출한다(W-01).
3. 담당자는 내부 검토를 수행한다. 예약 시점·철회·해제는 D-02 확정 뒤 적용한다. 공식 사전품의가 필요한 경우 실제 기관 절차를 거쳐 문서번호·결과를 따로 기록한다(D-06, W-02).
4. 사용 후 연구원은 동일 집행 건에 900,000원 최종 청구와 필요한 증빙을 제출한다. 서류 종류·단가·기한은 D-07 근거가 확보된 뒤 적용한다.
5. 담당자가 보완·검토확정을 처리한다. D-02/D-08 제안이 채택되면 최종 청구에 맞춰 예약 1,000,000원을 900,000원으로 조정한다. 두 금액을 더해 예약하지 않는다(W-03). 일부 청구라면 후속 예약을 임의 해제하지 않는다(W-04).
6. 담당자가 대학 ERP에서 직접 상신하고 본 시스템에는 문서번호·상신일·반려·재상신 결과만 기록한다. 등록만으로 지급완료가 되지 않는다(E-01/E-02). 외부 자동 연동은 없다.
7. 실제 지급 근거 확인 후 400,000원, 500,000원을 각각 기록한다. 부분 지급 시 예약 전환과 원장 반영을 한 거래로 처리하는 설계이며 중복 요청은 한 번만 반영한다(E-03/E-04).
8. 지급·증빙을 대조한 뒤 마감한다. 환입이 있으면 원지급·반환 근거·복원 연차를 확인하여 D-09에 따라 별도 이력을 남긴다. 과제책임자는 허용된 현황을 조회하며 진행의 승인자로 참여하지 않는다.

담당자·관리자의 대행 입력은 실제 입력자와 업무 주체를 함께 남긴다. 최초예산 10,000,000원이라는 가정에서 예약·부분지급별 가용액 계산은 [데이터 문서의 가상 예시](03-data-and-workflows.md)를 따른다. 사례 통과 여부는 미실행이며 [전체 검수표](06-acceptance.md)의 A/B/W/E/F/R 검수로 이후 확인한다.

## 합의가 필요한 화면 동작

- D-04: 공동 연구원·책임자가 타인 청구에서 볼 수 있는 상세 필드·증빙과 인수인계 범위. 확정 전에는 요약/상세를 같은 권한으로 취급하지 않는다.
- D-03/D-05: 연구원 예산변경 신청, 담당자 계정 발급·정지, 기관 로그인 방식.
- D-06/D-07: 공식 서식·비목/세목·필수 증빙·근거 적용일. 기존 Notion 명칭만으로 공식 코드를 추정하지 않는다.
- D-08/D-09: 다중 청구·실청구 묶음, 부분 지급·환입의 업무 화면 범위. 설계 초안을 운영 합의로 표시하지 않는다.
