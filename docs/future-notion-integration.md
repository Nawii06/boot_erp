# ERP 완료 후 Notion 실적 연계 방향

2026-11-05 / Asia/Seoul. 이번 문서는 향후 연계 때문에 ERP를 다시 설계하는 일을 줄이기 위한 방향과 경계를 정한다. 연계 기능 구현·Notion 접근·설정 변경을 실행한 문서가 아니다.

## 1. 사용자 확정 요구와 적용 순서

사용자는 ERP 구성을 완료한 뒤 실제 데이터를 입력하고, 그 이후 예산사용내역·현황을 Notion과 연계해 실적자료를 확인하기를 요청했다.

적용 순서는 다음과 같다.

1. ERP 기능과 운영 준비를 완료하고 권한·금액·전체 업무 흐름을 검수한다.
2. 승인된 실제 데이터를 입력·대조하고 기초잔액·신청·지급·증빙 연결의 정확성을 확인한다.
3. 실제 데이터가 검증된 뒤 별도 작업으로 Notion 실적 연계를 설계·구현·검수한다.

이 요구는 현 단계의 연계 구현이나 기존 Notion 원본 수정 허가를 뜻하지 않는다. 기존 Notion 원본의 읽기 전용 조건은 유지한다. 현재 ERP 기능 범위와 미결정 업무 정책은 [진행상황](STATUS.md), [요구사항](01-requirements.md), [결정기록](07-decisions.md)을 따른다.

## 2. 아직 확정하지 않은 사항

| 항목 | 현재 상태 | 확정할 내용 |
|---|---|---|
| 연계 방향 | 미확정 | ERP 결과를 Notion에 표시할지, Notion 자료를 ERP에서 조회할지, 자료 간 대조를 할지 |
| 대상 위치 | 미확정 | 기존 원본과 구분되는 페이지/DB 또는 다른 조회 방식 |
| 쓰기 권한 | 부여되지 않음 | 대상과 항목별 생성·수정·보관/제거 권한 및 수행 주체 |
| 실적 정의 | 미확정 | 신청·승인·실청구·지급·환입 중 어떤 사실을 어떤 기간 기준으로 확인할지 |
| 표시 단위 | 미확정 | 사업·연차·과제·비교과·예산항목·개별 신청 또는 집계 단위 |
| 갱신 방식 | 미확정 | 수동/정기 갱신, 주기·지연 허용시간·실패 알림 |
| 공개·열람 범위 | 미확정 | 사용자/역할별 수신 범위, Notion 공유 권한 및 재배정 시 처리 |
| 운영 원칙 | 미확정 | 외부 수정·충돌·재시도·정정·대조·중단 및 재개 절차 |

권고안은 ERP의 검증된 결과를 별도 실적 확인 영역에서 조회하게 하는 구조다. 이는 설계 제안이며 특정 Notion 페이지로의 전송, 일방향/양방향 동기화, 자동 갱신을 확정한 것이 아니다.

## 3. 기준자료와 운영 원장의 구분

- 예산금액·배정·분류는 Notion 등록 자료를 PDF보다 우선한다는 BC-11~BC-13을 유지한다. 미래 실적 연계가 이 기준을 자동 변경하지 않는다.
- 기존 Notion 자료를 입력 기준으로 이용할 때 원본 ID·조회시각·원본값·분류 매핑·대조 결과를 비공개로 보관한다. 원본 페이지를 운영 편의를 위해 수정하지 않는다.
- 실제 자료를 ERP에 입력한 뒤 발생하는 신청·승인·지급·환입은 해당 ERP의 업무 기록과 근거를 보존한다. 기존 Notion 수식/롤업을 검증된 지급 사실이나 ERP 잔액으로 자동 채택하지 않는다.
- 기초잔액을 입력하면서 그 잔액에 반영된 과거 변경·지급을 다시 합산하지 않는다. 최초예산부터 이력을 재구성할지, 기준시점 잔액과 참고 이력으로 시작할지는 실자료 입력 계획에서 하나로 정한다.
- 향후 외부 자료가 달라지면 불일치로 표시하고 원인을 대조한다. 연계 작업이 ERP의 확정 원장을 조용히 덮어쓰게 하지 않는다.

관련 근거: [금액·업무 설계](03-data-and-workflows.md), [이관·운영 원칙](09-data-and-operations.md), [예산 정책](budget-policy.md).

## 4. 현재 구현을 재사용할 부분과 누락된 부분

| 구분 | 현재 상태 | 향후 사용 방향 |
|---|---|---|
| 과제·업무·예산항목·집행건 | 불변 UUID와 관계가 존재 | 표시명 대신 내부 ID로 연결 |
| 분류·예산·초안·파일 | 버전·적용기간·분류 스냅샷·원 작성자/행위자 이력 존재 | 어떤 버전과 시점의 자료인지 추적 |
| 금액 | bigint 기반 원 단위 계산, JSON 문자열 직렬화 | 연계 계약에서도 정밀도 손실 방지 |
| 중복처리·감사 | 요청 ID·입력 지문·잠금·트랜잭션·변경 사건 존재 | 업무 원장 처리와 외부 전송의 중복처리를 구분해 설계 |
| 초안과 제출 건 | 현재 별도 구조, 제출 연결은 후속 범위 | ERP 완성 과정에서 초안→제출본→집행건의 추적 관계 명시 |
| 실제 지급·환입·보고서 | 현재 전체 운영 기능 미완성 | 완료·대조 전에는 실적 집계 완료로 표시하지 않음 |
| 외부 매핑·전송·운영 | Notion 어댑터·외부 ID 매핑·전송 큐·스케줄러·실패 대조 미구현 | 실제 데이터 입력 후 별도 단계에서 검토 |

## 5. 지금 준비할 최소 계약

현재는 문서화된 데이터 계약과 테스트 가능한 조회 구조까지만 준비한다. 외부 목적지가 없어도 ERP 내부 화면·보고서·내보내기에서 같은 집계 정의를 재사용할 수 있어야 한다.

### 식별과 자료 범위

- 과제·업무·예산항목·집행건·제출본의 안정 ID와 버전을 사용한다. ID를 과제명·파일명·화면 순번에서 재생성하지 않는다.
- 사업·연차·학년도·재원·사용기간과 분류 버전/표시명 스냅샷을 구분한다.
- 연계 계약의 버전을 두고 필드 추가·이름 변경·의미 변경을 구분한다. 외부 페이지 구조가 업무 테이블의 이름·관계를 결정하게 하지 않는다.
- 원본 Notion ID와 ERP ID의 매핑은 향후 별도 관리 대상으로 설계한다. API 토큰이나 외부 페이지 ID를 공개 샘플에 넣지 않는다.

### 금액과 실적의 의미

- 최초예산, 현재예산, 유효 신청 차감액, 가용액, 내부 승인액, 실제 지급액, 환입액, 순지급액을 서로 다른 사실로 정의한다. 미구현 집계는 숫자 0을 실제 결과처럼 표시하지 않는다.
- 현재 정책상 `가용액 = 현재예산 - 유효 신청 차감액`이다. 승인·지급 시 같은 신청 금액을 다시 차감하지 않는다.
- 지급 후 환입이 가용액을 어떻게 바꾸는지는 확정될 환입 정책에 따른다. 단순히 지급액에서 환입액을 뺀 값과 가용예산 복원을 같은 사실로 취급하지 않는다.
- ‘실적’의 최종 정의가 정해지기 전에는 신청액이나 승인액을 지급 실적으로 이름만 바꿔 표시하지 않는다.
- 집계 조인으로 동일 신청·지급·첨부 연결이 중복 합산되지 않게 한다. 원 단위 정수와 문자열 계약을 유지한다.

### 시점과 스냅샷

- 기준시각, 조회 기간, 날짜 기준(신청일/사용일/지급일 등), 시간대, 계산 정의 버전을 표시한다.
- 행 목록·항목 합계·과제 합계가 같은 기준시점의 결과가 되도록 조회한다. 현재 잔액과 기간 지급액을 같은 성격의 값으로 표시하지 않는다.
- 외부 표시 결과에는 원장/자료 버전, 생성시각, 최종 성공 갱신시각, 최신 여부를 확인할 수 있게 하는 안을 준비한다. 전송 성공시각을 업무 발생시각으로 대체하지 않는다.

### 권한과 최소 공개

- ERP 화면·상세·파일·집계·내보내기에 적용되는 역할·배정 조건을 동일한 조회 서비스에서 적용한다. Notion 서비스 계정의 넓은 접근 권한으로 사용자별 범위 검사를 우회하지 않는다.
- 연구원 간 개별 업무·지출·증빙은 비공개, 책임자는 담당 과제·비교과 조회 전용이라는 정책을 유지한다. 공통 예산 마스터 조회 권한을 다른 연구원의 개별 자료 공개 권한으로 확대하지 않는다.
- 집계 자체로 개인 자료가 드러날 수 있으므로 대상·단위·열람자별 공개 가능 여부를 확인한다. 개인정보·계좌·인증정보·소득정보·증빙 원문·다운로드 링크는 기본 전송 항목에 포함하지 않는 안을 우선 검토한다.
- 재배정·배정 해제·계정 정지 후에는 원 작성자/이력을 보존하면서 현재 열람 권한을 다시 평가한다. 과거에 복사된 자료의 접근 회수는 별도 대상 권한과 보관 정책이 필요하며 ERP의 권한 변경만으로 자동 해결된다고 보장하지 않는다.

## 6. 실제 연계 단계에서 갖출 운영 설계

아래는 미래 구현의 검토 항목이다. 지금 큐·자격증명·스케줄러를 생성하거나 전송을 실행하지 않는다.

- 업무 원장 트랜잭션과 외부 통신을 분리한다. 외부 지연·장애가 신청·승인·지급의 원자성을 깨지 않게 한다.
- 대상 ID 매핑과 원본 버전·계약 버전을 기준으로 중복을 방지한다. 동일 배치/버전을 다시 실행해도 중복 자료가 생기지 않게 한다.
- 일부 성공 후 재시도, 오래된 작업의 늦은 도착, 순서 역전, 연결 중단 후 재개를 다룬다. 최신 데이터를 오래된 스냅샷으로 덮어쓰지 않는다.
- 성공/실패·오류분류·재시도·최종 성공시점·건수와 금액 총계 대조를 기록한다. 오류 로그에 실제 개인정보·증빙·자격증명을 넣지 않는다.
- Notion의 수동 변경과 ERP 결과가 다를 때 적용할 충돌 정책을 정한다. 원장 자동 역반영은 별도 명시적 범위 결정 없이는 하지 않는다.
- ERP 정정·취소·환입·권한 변경을 외부 표시에서 어떻게 반영할지 정한다. 원장 이력은 보존하고 외부의 제거/숨김/정정은 대상별 허용된 방식으로 수행한다. 외부 항목을 제거하기 위해 ERP 원장을 삭제하지 않는다.
- 복구·재구축 시 ERP 집계와 외부 결과를 다시 대조할 수 있어야 한다. 외부 서비스 장애 때 ERP 자체의 실적 조회는 계속 가능하게 한다.

## 7. 단계별 검증 조건

| 시점 | 검증 조건 |
|---|---|
| ERP 구성 중 | 안정 ID/버전, 정확한 금액, 동일 집계 서비스, 기준시점 표시, 권한 있는 조회를 가상 자료로 검증 |
| 실제 입력 전 | 대상·기준시점·기초잔액 방식·배치 ID·분류 매핑·백업/복구·비공개 보관 위치 확정 |
| 실제 입력 후 | 원본/입력 건수·현재예산·유효 차감·가용액·실제 지급/환입·파일 연결 대조, 중복/누락/불명확 상태 분리 |
| Notion 연계 시작 전 | 대상·방향·쓰기 권한·공개 범위·실적 정의·주기·정정/권한회수 방식 확정 |
| 연계 검수 | 격리 대상에서 재시도·부분 실패·오래된 버전·불일치·권한 해제·정정·재구축 검증 후 실제 대상 적용 |

검수 예시는 정확한 원 단위 경계, 신청 후 승인/지급의 중복 차감 방지, 첨부 다중 연결의 중복 합산 방지, 배정 해제와 후임 승계, 같은 배치 재시도, 이전 스냅샷 재실행, 부분 실패 후 총계 대조다. 현재 미구현 연계 검수를 이미 통과했다고 기록하지 않는다.

## 8. 현재 작업에서 하지 않는 일

Notion 페이지/DB 생성·수정·삭제·권한 변경, 실제 원본 조회·내보내기, 토큰 발급/저장, 매핑 테이블·전송 outbox·스케줄러·자동화 구현, 실데이터 전송은 이번 설계 범위에 포함하지 않는다. 사용자 요구·확정 업무 정책·검증된 현재 코드와 연결된 계약만 준비한다.
